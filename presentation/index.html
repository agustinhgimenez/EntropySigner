01 // MOTIVACIÓN

El Problema Fundamental

Criptografía Asimétrica & HD Wallets
  • La wallet ES la clave privada: No existe entidad bancaria, soporte técnico ni botón de "recuperar contraseña". El control de los fondos depende del conocimiento exclusivo del secreto.
  • Dependencia crítica de 256 bits: La custodia soberana descansa en un único número pseudoaleatorio generado una sola vez en la vida del dispositivo.
  • Fallas históricas catastróficas por generadores débiles:
    Vulnerabilidad "Milk Sad" (Libbitcoin Explorer, 2023): Semillas sembradas con un timestamp de 32 bits. Se redujo el espacio de búsqueda a sólo $2^{32}$ combinaciones, permitiendo el robo masivo de billeteras en minutos.
  • Pregunta central de investigación: ¿Cómo generar, aislar, validar y operar con seguridad una clave criptográfica de 256 bits en un microcontrolador accesible sin conexión a red?

04 // FUNDAMENTO CRIPTOGRÁFICO

El Rol del LDR y el Extractor SHA-256

NIST SP 800-90B Compliance
  • Regla de oro: SHA-256 no crea entropía.
    Por la desigualdad de Rényi: $H_{\min}(\text{salida}) \le \min(256, H_{\min}(\text{entrada}))$. Un hash oculta estructura y uniformiza la distribución, pero no puede transformar datos predecibles en aleatorios.
  • ¿Por qué el LDR tiene crédito de entropía 0?
    La luz ambiente es controlable externamente (una linterna satura el ADC en 4095; una tapa lo apaga a 0). No cumple el estándar NIST SP 800-90B de modelado estocástico independiente.
  • Defensa en profundidad:
    La fuente criptográfica primaria es el TRNG interno del ESP32-S3. El LDR suma variabilidad física que jamás debilita la salida en caso de un RNG sano.

06 // MNEMÓNICOS

BIP-39: Codificación y Respaldo Humano

src/bip39/bip39.cpp
  • 256 bits de entropía $\rightarrow$ 24 palabras:
    1. Calcula $\text{SHA-256}(\text{entropía})$ y extrae los primeros 8 bits como checksum.
    2. Concatena: 256 bits de entropía + 8 bits de checksum = 264 bits.
    3. Divide en 24 paquetes de 11 bits: $24 \times 11 = 264$.
    4. Cada valor $[0, 2047]$ indexa la Wordlist oficial de 2048 palabras en inglés.
  • Detección de errores garantizada: Si el usuario transcribe una palabra errónea o altera el orden, el checksum de 8 bits detecta el error con un 99.6% de probabilidad ($1 - 1/256$).
  • Derivación a Semilla:
    $\text{Seed} = \text{PBKDF2-HMAC-SHA512}(\text{password}=\text{mnemonic}, \text{salt}=\text{"mnemonic"}+\text{passphrase}, 2048 \text{ iteraciones}) \rightarrow 64 \text{ bytes (512 bits)}$.
07 // CRIPTOGRAFÍA ELÍPTICA

BIP-32: HD Wallets sobre secp256k1

src/bip32/bip32.cpp
  • Generación de Clave Maestra:
    $\text{HMAC-SHA512}(\text{Key} = \text{"Bitcoin seed"}, \text{Data} = \text{Seed}) \rightarrow (I_L, I_R)$.
    $I_L = \text{Clave privada maestra}$ ($k \in [1, n-1]$), $I_R = \text{Chain Code maestro}$.
  • Derivación Endurecida (Hardened) vs Normal:

    Hardened ($i \ge 2^{31}$)

    $\text{Data} = \mathtt{0x00} \parallel k_{\text{padre}} \parallel i$

    ✓ Si una clave hija se compromete, es matemáticamente imposible derivar la clave padre.

    Normal ($i < 2^{31}$)

    $\text{Data} = K_{\text{pub\_padre}} \parallel i$

    Permite auditoría con Extended Public Keys (xpub) sin claves privadas.

  • Aritmética sobre la curva elíptica de Koblitz: $y^2 = x^3 + 7 \pmod p$ utilizando mbedTLS ECP y HMAC-SHA512.
08 // MULTI-CURRENCY

Bitcoin y Ethereum (BIP-44)

src/bitcoin/ & src/ethereum/

₿ Bitcoin (m/44'/0'/0'/0/0)

  • Clave pública comprimida (33 bytes): $\mathtt{02/03} \parallel X$.
  • $\text{HASH160} = \text{RIPEMD-160}(\text{SHA-256}(K_{\text{pub}}))$.
  • Codificación Base58Check con versión byte 0x00 (Mainnet).
  • Genera direcciones clásicas P2PKH que inician con 1...

Ξ Ethereum (m/44'/60'/0'/0/0)

  • Descompresión de coordenadas $(X, Y)$ (64 bytes).
  • $\text{Hash} = \text{Keccak-256}(X \parallel Y)$ (padding 0x01).
  • Dirección cruda = últimos 20 bytes del hash.
  • Checksum EIP-55 (mayúsculas/minúsculas según el hash del texto).
09 // SEGURIDAD DE MEMORIA

Protección Contra Optimizaciones del Compilador

src/security/secure_mem.h
  • El peligro de memset(): El compilador (GCC con -O2/-O3) aplica Dead Store Elimination. Si un buffer de claves sale de ámbito, el compilador descarta la limpieza porque "nadie volverá a leerla".
  • Nuestra solución en EntropySigner: 
    inline void secureMemzero(void* ptr, size_t len) {
    if (ptr == nullptr) return;
    volatile uint8_t* p = static_cast<volatile uint8_t*>(ptr);
    while (len--) {
        *p++ = 0; // Puntero volatile fuerza la escritura en bus de memoria
    }
#if defined(__GNUC__)
    // Barrera de compilador: clobber "memory" impide mover o elidir escrituras
    __asm__ __volatile__("" : : "r"(ptr) : "memory");
#endif
}
  • Ciclo de vida efímero: La semilla y la clave maestra solo viven durante la derivación y se destruyen antes de mostrar las direcciones públicas en pantalla.

12 // SEGURIDAD REALISTA

Modelo de Amenazas & Honestidad Académica

docs/SECURITY.md

Garantías Reales

  • Air-Gapped: Cero código de red. WiFi y Bluetooth inhabilitados a nivel de binario.
  • Memoria volátil: Ningún secreto se persiste en Flash, NVS ni EEPROM.
  • Cero filtraciones por Serial: En modo PRODUCTION los logs de depuración se eliminan en compilación.

Limitaciones del Prototipo

  • Sin Secure Element: Vulnerable a lectura física con microscopio o sondas ante robo del chip.
  • Sin Secure Boot / Flash Cifrada: Un atacante con acceso USB físico puede flashear un firmware malicioso.
  • Sin protección contra canales laterales: Curva elíptica no protegida contra DPA (análisis de consumo).
